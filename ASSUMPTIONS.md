# Assumptions

Decisions the brief did not specify, and how this implementation resolves each one. They were taken one by one while
building and are recorded with their reasoning in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md). Where a choice is easy to
change, the setting or place is named. The request/response shapes themselves are frozen in
[`docs/API_CONTRACT.md`](docs/API_CONTRACT.md).

## Identity and input

1. **Identity is the `X-Student-Id` header and nothing more.** It must be exactly 17 digits (`^[0-9]{17}$`). There is no
   login, token or password: whoever sends a valid id acts as that student. A missing or malformed header is
   `400 INVALID_STUDENT_ID`. *Why:* the contract names only the header; authentication is not specified.
2. **The header is checked before anything else.** A bad header on an unknown class is a 400, not a 404, so a bad request
   never reveals whether a class or hold exists.
3. **`GET /holds/{holdId}` takes no header**, because the contract lists none. Anyone who knows a hold id can read its
   status; the response deliberately leaves out `studentId`.
4. **Class input.** `name` must not be blank (spaces only counts as blank), at most 200 characters as sent (200 matches the
   column size) and contain no NUL character; it is stored with surrounding spaces trimmed. `totalSeats` must be a positive
   whole number. Class names do not have to be unique. Anything else is `400 VALIDATION_ERROR`.
5. **Ids are generated by the server** (`c_` and `h_` followed by a GUID). Clients never choose them.

## Seats and holds

6. **A seat is held, confirmed or free.** `availableSeats = totalSeats - heldSeats - confirmedSeats`, never negative.
   A hold past its expiry is not counted as held.
7. **One active hold per student per class.** "Active" means HELD or CONFIRMED (the contract's "active hold or confirmed
   admission"). A second attempt is `409 DUPLICATE_ACTIVE_HOLD`, even if the class has meanwhile filled up (the student is
   told "duplicate", not "sold out"). A student may hold a seat in several different classes at once, and one student never
   blocks another. After a hold is cancelled or expires the student may hold again; the old holds stay on record.
8. **Hold window.** `HOLD_DURATION_SECONDS`, default 600 (10 minutes), configurable, must be greater than 0.
   `expiresAt` is the moment of the hold plus the window, in UTC. The window is fixed: nothing extends or renews it.
9. **Expiry is exact and computed from the stored time, not from a timer.** A HELD hold is EXPIRED from the instant
   `expiresAt` is reached. The `GET` endpoints report it as EXPIRED and `GET /classes` counts the seat as free straight
   away, so expiry is right even if the API was down or the background job is off. The background job (every 5 seconds,
   `HOLD_EXPIRY_SWEEP_INTERVAL_SECONDS`) only tidies the stored rows.
10. **"First come, first served" means the order in which the database commits the seat claims.** There is no waiting
    list or queue: when no seat is free the request is refused at once with `409 NO_SEAT_AVAILABLE`, and the student can
    try again after a cancellation or expiry releases a seat.
11. **A class is never oversold, even with several API instances.** A seat is claimed by one atomic database statement and
    the database refuses any state with more seats taken than exist, so any number of API processes can share one
    database. Expiry is judged against each API server's own UTC clock, so server clocks are assumed to be in sync.
12. **Confirming stands for payment.** The brief has students pay to confirm, but the contract has no payment endpoint, so
    `POST /holds/{holdId}/confirm` is the moment payment is deemed complete. No payment is processed or modelled.
13. **Confirm.** Only the owner can confirm, and only a hold that is still HELD and not yet expired. The owner confirming
    again gets 200 and the seat is not counted twice (idempotent, per the contract). Another student gets
    `409 NOT_HOLD_OWNER`; this is checked before the hold's status, so a non-owner can neither learn that status nor use the
    idempotent path. An expired hold is `409 HOLD_EXPIRED`, a cancelled one `409 HOLD_CANCELLED`. A confirmed admission is final.
14. **Cancel (`DELETE`).** Only the owner can cancel, and only while the hold is HELD and not expired. The seat is available
    again immediately, not at the original expiry time. Anything else is a `409` with its own code: `NOT_HOLD_OWNER`,
    `HOLD_EXPIRED`, `HOLD_CANCELLED` or `HOLD_ALREADY_CONFIRMED`. Cancelling twice is a 409 rather than a second 204, and a
    confirmed admission cannot be cancelled through the API.
15. **`GET /me/holds`** returns every hold of the student, whatever its status, newest first, with the class name, and
    `[]` if there are none. Lists are not paginated; `GET /classes` returns every class ordered by name, then id.

## Errors

16. **Status codes.** 400 for missing or malformed input, 404 for an unknown id, 409 for a state conflict (no seat,
    duplicate, wrong owner, expired, cancelled, already confirmed). Every error body is exactly
    `{ "error": "SOME_CODE", "message": "..." }`: the codes are stable, the messages are for people.
17. **No HTTP 500 on any student endpoint.** Anything unexpected is logged in full and answered with a 4xx in the same
    shape: a database conflict or deadlock is `409 CONFLICT` (safe to retry), a value the database refuses is
    `400 INVALID_INPUT`, anything else is `400 UNEXPECTED_ERROR` with a reference id (also sent as the `X-Correlation-Id`
    header and attached to every log line of the request). No exception text, SQL or stack trace ever reaches the client.
    400 is the generic 4xx chosen for the catch-all; it is one constant in `ExceptionMapper`.
18. **Framework errors use the same shape** (unknown route `404 ROUTE_NOT_FOUND`, wrong method `405 METHOD_NOT_ALLOWED`,
    wrong content type `415 UNSUPPORTED_MEDIA_TYPE`). The exception: the web server rejects a few malformed requests before
    the application runs (a `%00` in the URL path, a broken request line, oversized headers) with its own bare 400/431.
    **A request body must be UTF-8 JSON.** A `Content-Type` that names any other charset (`utf-16`, `utf-32`, `iso-8859-1`,
    ...) or that cannot be parsed (`application/json; charset=`) is `415 UNSUPPORTED_MEDIA_TYPE`, never the catch-all
    `UNEXPECTED_ERROR`. JSON exchanged between systems is UTF-8 (RFC 8259), and UTF-16 used to be accepted only by accident of
    the framework's decoder, which crashed on any body that was not valid UTF-16. The header is judged only when the request
    has a body.
19. **`GET /health` is an extra endpoint** beyond the eight in the contract: 200 when the database answers within 3 seconds,
    otherwise `503 DATABASE_UNAVAILABLE`. It is the only intended 5xx, because it is an infrastructure probe rather than a
    student endpoint.

## Operation

20. **All state lives in PostgreSQL.** Restarting the API loses nothing: classes, holds, confirmed seats and expiry times
    are as they were, and a hold that runs out while the API is down is already expired when it comes back.
21. **The application creates its own schema.** Migrations are applied at startup; Docker Compose starts the API only after
    PostgreSQL is healthy.
22. **Plain HTTP, and Swagger is on in every environment** so a reviewer can try the API straight away. The container
    serves HTTP only, on port 8080; TLS would be terminated by a reverse proxy in front.
23. **Timestamps are UTC (ISO 8601, ending in `Z`).** The database keeps microseconds, so the `expiresAt` in the response
    that creates a hold can show one more fractional digit than the same hold read back later; the two differ by less than
    a microsecond.
24. **Browsers may call the API only from an explicit list of origins (CORS).** `CORS_ALLOWED_ORIGINS` is a comma-separated
    list of origins (scheme, host, port), default `http://localhost:5173,http://localhost:4173` (the frontend's dev and
    preview servers). Entries are matched exactly: no wildcard, and a malformed value stops the API at startup. Blank means
    no origin, so CORS is off. Only `GET`, `POST` and `DELETE` and the `Content-Type` and `X-Student-Id` request headers are
    allowed, `X-Correlation-Id` is readable by pages, and error responses carry the headers too. Callers that send no
    `Origin` header (curl, other servers) are unaffected. *Why:* the frontend is served from its own origin, and without
    this a browser discards every response. This is not access control: a request from another origin is still answered,
    the browser just will not give it to that page (assumption 1 still holds). No contract field or status changed.
25. **One API instance holds at most 30 database connections** (`Maximum Pool Size`, default 30; `DB_MAX_POOL_SIZE` in
    Docker Compose; a value in the connection string always wins). PostgreSQL's default `max_connections` is 100 with 3 kept
    for superusers, so three instances of 30 fit (90 of 97). *Why:* with Npgsql's own default of 100 per process, one instance
    could keep nearly every connection the server has after a burst, and another instance's requests then failed with
    `53300 too many clients already` (seen by the student as `400 UNEXPECTED_ERROR`). Seat safety never depended on this: it is
    enforced in the database. If all 30 connections are busy a request waits for one (Npgsql's 15-second connection timeout
    applies) instead of being refused at once.

## Out of scope

Authentication or authorization beyond the header, payment processing, a waiting list, pagination, rate limiting, and any
notion of admission years, shifts or student profiles. None is mentioned in the brief or the contract.

## Known limitations

- The student-id pattern accepts a trailing newline (`$` also matches before a final `\n` in .NET). A header value cannot
  contain a newline over HTTP, so it is not reachable; a skipped unit test documents it, and the fix is `\z` in place of `$`.
- The few requests the web server rejects before the application runs (assumption 18) cannot be given the standard error shape.

## Known test failures

**None at submission.** On 2026-11-11 `cd backend && dotnet test` passed in full, twice: 174 unit tests passed and 1 was skipped
on purpose (the trailing-newline test above), and 273 integration tests passed. The second run was on a clean export of the
committed code.

One thing is not settled. An earlier run (Session 16) recorded 7 integration failures: `HoldExpirySweeperTests` 2,
`MultiProcessSeatRaceTests` 2, `RestartPersistenceTests` 2 and `SeatRaceTests` 1. They did not reproduce, and their assertion
messages were never saved, so what each one said is unknown.

- **Best guess:** machine load, not a defect in the application or a wrong assertion. That run logged Npgsql
  `Timeout during reading attempt` errors and race rounds of 20-38 s (about 0.6 s on a healthy machine) with roughly 500 MB of
  RAM free. Npgsql's default command timeout is 30 s, which is the same size as those rounds. This is an inference from the
  logs, not something that was reproduced.
- **Evidence it is load-sensitive but not fragile:** during the second run other test runs were using the same machine and
  Docker, and the run took 7.0 min instead of 4.6 min. The heaviest race and cleanup tests ran about three times slower, and
  all of them still passed.
- **With more time:** run the four classes (`SeatRace`, `MultiProcessSeatRace`, `RestartPersistence`, `HoldExpirySweeper`) with
  Docker limited to about 1 GB of RAM and one or two CPUs, and save the failure messages. Then check whether the tests need a
  larger `Command Timeout` in their connection strings, or a sampler loop that does not spin (`SeatRace.cs` queries the
  database back to back for the whole race), or no change at all.
