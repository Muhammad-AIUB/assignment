# Architecture Decisions

Append-only decision log. One entry per decision: date, decision, reason.
Backend decisions come first and frontend decisions last, each under its own heading.

# Backend decisions

## Session 1 — Database layer

- **String IDs with prefixes** (`c_<guid>`, `h_<guid>`) generated in the entity, matching the contract's id format. Columns are `varchar(64)`.
- **Status stored as string** (`Held`, `Confirmed`, `Expired`, `Cancelled`) via EF value conversion; readable in SQL and safe against enum reordering. The API layer maps to the contract's uppercase values later.
- **Timestamps are UTC** `timestamptz` (`DateTime`, Kind=Utc required by Npgsql).
- **Indexes on `holds`:** `(ClassId, StudentId, Status)` for the "active hold exists" check; `(ClassId, Status)` for seat counting; `(Status, ExpiresAt)` for expiry sweeps; `(StudentId)` for `GET /me/holds`.
- **Constraints:** `classes.TotalSeats > 0` check; FK `holds.ClassId -> classes.Id` with `RESTRICT`.
- **Not added yet (open for the hold-creation session):** a partial unique index on `(ClassId, StudentId)` where `Status IN ('Held','Confirmed')` would enforce the one-active-hold rule at the DB level. Deferred because expired-but-unswept HELD rows would block re-holding until business rules define expiry handling.
- **`HOLD_DURATION_SECONDS`** read from configuration/env var (default 600, must be > 0, validated on startup) into `HoldOptions`, injectable as `IOptions<HoldOptions>`.
- **Migrations** live in `Infrastructure/Persistence/Migrations` and are applied automatically on Api startup. A design-time factory lets `dotnet ef` run without booting the Api host. `dotnet-ef` is a local tool (`dotnet tool restore`).
- **Missing `ConnectionStrings:Postgres`** now fails fast at startup with a clear message.

## Session 2 — Class endpoints (POST /classes, GET /classes, GET /classes/{id})

- **Service layer lives in `Api/Services`** (`IClassService`/`ClassService`) and uses `AppDbContext` directly; controllers only validate -> call service -> map to HTTP. A repository layer was not added: nothing needs it yet.
- **Seat counts in one SQL statement**: held/confirmed are correlated `COUNT` subqueries per class (backed by `ix_holds_class_status`). Expired-but-unswept HELD rows (`ExpiresAt <= now`) are excluded from `heldSeats`. `availableSeats = max(0, total - held - confirmed)`, computed in memory after the query (EF could not translate `Math.Max` inside a DTO constructor projection).
- **Clock via `TimeProvider`** (singleton `TimeProvider.System`) so "now" is injectable.
- **Standard error shape for validation**: `InvalidModelStateResponseFactory` returns `{ "error": "VALIDATION_ERROR", "message": ... }` with 400 for both FluentValidation failures and model-binding errors (missing/malformed body). Unknown class -> 404 `CLASS_NOT_FOUND`.
- **Validation**: `name` non-empty (whitespace rejected), max 200 chars (matches the column, so over-long names are a 400 rather than a DB error); `totalSeats > 0`. Name is trimmed before saving.
- **Not yet built**: global exception-handling middleware (unexpected exceptions still fall to the framework default).

## Session 3 — POST /classes/{classId}/holds (concurrency control)

**Note:** `docs/BUSINESS_RULES.md` still does not exist in the repo. "Rule 1" was implemented as *seats are never oversold (held + confirmed <= total)* and "rule 3" as *a student has at most one active (HELD/CONFIRMED) hold per class*, as described in the session prompt and API contract.

**Approach: atomic conditional UPDATE on the class row, in one transaction (READ COMMITTED).**
`classes` gained denormalised counters `HeldSeats` and `ConfirmedSeats`. Creating a hold runs:

1. *(cleanup)* Flip this class's expired HELD holds to EXPIRED and decrement `HeldSeats` by exactly the number flipped (single CTE statement).
2. *(seat claim)* `UPDATE classes SET HeldSeats = HeldSeats + 1 WHERE Id = @id AND HeldSeats + ConfirmedSeats < TotalSeats RETURNING HeldSeats`. No row returned = sold out -> 409 `NO_SEAT_AVAILABLE`.
3. *(rule 3)* Check for an existing HELD/CONFIRMED hold for (class, student). If found, **roll back** (undoing step 2) -> 409 `DUPLICATE_ACTIVE_HOLD`.
4. Insert the `Hold` row and commit.

**Why this is safe under concurrency and across processes**
- The check ("is there a seat?") and the reservation (increment) are one SQL statement, so there is no read-then-write gap for another request to slip into. The decision is made by PostgreSQL against the current committed row, not by app memory that may be stale.
- The UPDATE takes a row-level lock on the class row that is held until the transaction ends. A concurrent UPDATE on the same row blocks, then (READ COMMITTED) re-evaluates the `WHERE` against the freshly committed row. With N seats left, exactly N claims match; later ones match zero rows.
- All of this lives in the database, so it holds regardless of how many API processes/threads run against it. No in-process locks or caches are involved.
- **Rule 3 is race-safe** because step 3 runs *after* the class-row lock is acquired in step 2: all create-hold transactions for a class are serialised from that point to commit, so a competing transaction's hold is either already committed (and visible to the check's fresh statement snapshot) or has not yet reached its own check. Two simultaneous requests from the same student therefore cannot both pass. Different classes do not contend with each other.
- **Defence in depth:** `ck_classes_seats_not_oversold` (CHECK held >= 0, confirmed >= 0, held + confirmed <= total) makes the DB refuse an oversell even if code were wrong, and the partial unique index `ux_holds_active_student_class` on `(ClassId, StudentId) WHERE Status IN ('Held','Confirmed')` enforces rule 3 at the DB level (a violation is mapped to the same 409). This resolves the Session 1 deferral: expired-but-unswept rows are now flipped to EXPIRED in step 1 before the insert, so they no longer block a re-hold.
- No deadlocks: the transaction only locks hold rows in step 1 (before taking the class lock in step 2 for the same class), and never locks hold rows after the class lock, so there is no lock-order cycle.

**Other decisions**
- Raw ADO.NET commands on EF's transaction are used for the two statements because EF's `SqlQuery` wraps SQL in a subquery, which Postgres cannot do for `UPDATE ... RETURNING`.
- `GET /classes` still derives counts from `holds` (Session 2); the new counters are authoritative for seat admission. They differ only transiently for expired-but-unswept holds, which `GET` already excludes. Later sessions (confirm / cancel / expiry sweep) must update the counters with the same atomic-UPDATE style.
- Invalid `X-Student-Id` -> 400 `INVALID_STUDENT_ID`; unknown class -> 404 `CLASS_NOT_FOUND`; the header is validated before the class lookup.
- Migration `AddSeatCountersAndActiveHoldIndex` backfills counters from existing rows.

## Session 4 — GET /holds/{id}, POST /holds/{id}/confirm, DELETE /holds/{id}, GET /me/holds

**Note:** `docs/BUSINESS_RULES.md` still does not exist. As in Session 3, the rules were taken from the session prompt and `API_CONTRACT.md`: *rule 2* = expiry is computed lazily (a HELD hold past `ExpiresAt` is EXPIRED even if nothing has swept it), *rule 5* = confirm is idempotent for the owner and never counts a seat twice, and the delete assumption = only the owner can cancel, only a HELD (unexpired) hold, anything else is 409.

**Lazy expiry (rule 2).** `Hold.EffectiveStatus(stored, expiresAt, now)` (Domain) is the single definition: stored `Held` with `ExpiresAt <= now` is `Expired`; every other status is returned as stored. `GET /holds/{id}` and `GET /me/holds` apply it in memory to the stored row, so no background job is needed to report EXPIRED. GETs never write. The boundary (`ExpiresAt <= now` is expired) matches the SQL in the seat claim and cleanup.

**Confirm and cancel share one atomic transition** (`HoldService.TransitionAsync`), the same pattern as the Session 3 seat claim, one statement that decides and applies:

```sql
WITH moved AS (
    UPDATE holds SET <Status = 'Confirmed', ConfirmedAt = @now | Status = 'Cancelled'>
    WHERE "Id" = @holdId AND "StudentId" = @studentId AND "Status" = 'Held' AND "ExpiresAt" > @now
    RETURNING "ClassId")
UPDATE classes SET <HeldSeats - 1, ConfirmedSeats + 1 | HeldSeats - 1>
WHERE "Id" IN (SELECT "ClassId" FROM moved)
RETURNING "Id"
```

- The `WHERE` on the hold row *is* the rule check (owner, still HELD, not expired). Only a row that passes it changes status, and the class counters move only for that returned row, in the same statement and transaction. Counters therefore cannot drift from hold statuses.
- Concurrent requests on the same hold queue on the hold row lock and re-check the guard under READ COMMITTED. So N parallel confirms by the owner produce one transition and the other N-1 fall through to the 200 idempotent path with the counters untouched; a confirm racing a cancel has exactly one winner; N parallel cancels release the seat exactly once. Tests cover all three.
- Delete releases the seat in the same statement (`HeldSeats - 1`), so the seat is available immediately, not at expiry. A cancelled hold is no longer in the partial unique index, so the student may hold again.
- Lock order is hold row then class row, the same as the Session 3 expiry cleanup, so there is no deadlock cycle with hold creation.
- Raw ADO.NET is used through the existing `ExecuteScalarAsync` helper (EF cannot express a data-modifying CTE). The SQL fragments that vary are compile-time constants; request values are always parameters.

**When the guarded UPDATE matches nothing** the reason is read from committed state (the UPDATE waited on any competing transaction, so that state is final), in this precedence: no row -> 404 `HOLD_NOT_FOUND`; not the owner -> 409 `NOT_HOLD_OWNER` (checked before status, so another student cannot learn a hold's state and cannot use the idempotent path); then by effective status: Confirmed -> 200 for confirm (idempotent) / 409 `HOLD_ALREADY_CONFIRMED` for delete; Cancelled -> 409 `HOLD_CANCELLED`; Expired -> 409 `HOLD_EXPIRED`. An active, owned HELD hold with a failed guard is unreachable, so that case throws.

**Expired holds are not written by confirm/cancel.** An expired-but-unswept hold is rejected with 409 and left as is; confirm/cancel never touch it, so they cannot corrupt `HeldSeats`. It is still not counted by `GET /classes`, and the next `POST /classes/{id}/holds` for that class sweeps it (Session 3 step 1). A standalone background sweep was not added; it is not needed for correctness.

**Other decisions**
- `X-Student-Id` is validated (400 `INVALID_STUDENT_ID`) before any lookup on confirm, delete and `/me/holds`, reusing one controller helper that `POST /classes/{id}/holds` now also uses. `GET /holds/{id}` takes no header (per the contract) and is readable by anyone who knows the id.
- `GET /me/holds` returns the student's holds of every status (the contract's four statuses all apply), newest first (`CreatedAt` desc, then `Id`), joined to the class name; an empty list is `[]`. Served by `ix_holds_student`.
- Response bodies are exactly the contract's fields; `GET /holds/{id}` does not include `studentId`.

## Session 5 — Background expiry sweep, GET /health

**Note:** `docs/BUSINESS_RULES.md` still does not exist; nothing in this session needed a business rule beyond Sessions 2-4.

**The expiry sweep is housekeeping, not correctness.** A hold past `ExpiresAt` is already EXPIRED as far as the API is concerned, by computed logic that needs no sweep: `Hold.EffectiveStatus` (GET /holds, GET /me/holds), the expired-excluding counts in GET /classes, and the per-class cleanup at the top of the seat claim in POST /classes/{id}/holds. The sweep only makes the stored rows and the `HeldSeats` counters match, for data cleanliness. This is stated in code comments on `HoldExpiryWorker` and `HoldExpirySweeper`, and a test (`Sweep_changes_nothing_the_api_reports`) checks the API gives identical answers before and after a sweep.

**Shape.** `IHoldExpirySweeper`/`HoldExpirySweeper` (Api/Services) does one sweep and returns how many holds it expired. `HoldExpiryWorker` (Api/BackgroundServices, a `BackgroundService`, so an `IHostedService`) calls it from a `PeriodicTimer`, once immediately on start and then every interval, in a fresh DI scope per tick (the sweeper owns a scoped `DbContext`). Config, read like `HOLD_DURATION_SECONDS`: `HOLD_EXPIRY_SWEEP_INTERVAL_SECONDS` (default 5, must be > 0, validated on startup) and `HOLD_EXPIRY_SWEEP_ENABLED` (default true). A failed sweep is logged as a warning and retried next tick; it never stops the host. The shared test factory sets `HOLD_EXPIRY_SWEEP_ENABLED=false` so tests that deliberately leave expired rows unswept (to prove lazy expiry) are not changed under them; the sweeper tests call the sweeper directly and one test turns the worker on for its own host.

**The sweep statement** (one SQL statement per batch of 500, in a READ COMMITTED transaction; the `(Status, ExpiresAt)` index from Session 1 serves it):

```sql
WITH due AS (SELECT "Id" FROM holds WHERE "Status" = 'Held' AND "ExpiresAt" <= @now
             ORDER BY "ExpiresAt" LIMIT @batch FOR UPDATE SKIP LOCKED),
     expired AS (UPDATE holds h SET "Status" = 'Expired' FROM due
                 WHERE h."Id" = due."Id" AND h."Status" = 'Held' AND h."ExpiresAt" <= @now
                 RETURNING h."ClassId"),
     per_class AS (SELECT "ClassId", count(*) AS n FROM expired GROUP BY "ClassId"),
     released AS (UPDATE classes c SET "HeldSeats" = c."HeldSeats" - per_class.n
                  FROM per_class WHERE c."Id" = per_class."ClassId" RETURNING 1)
SELECT count(*) FROM expired
```

- **Counters cannot drift.** The decrement per class is the number of rows the guarded UPDATE actually flipped (`RETURNING`), applied in the same statement and transaction, the same pattern as Sessions 3-4. This relies on the invariant `HeldSeats = number of HELD rows` (unswept expired rows included), which every writer and the Session 3 migration backfill maintain. Data that breaks it makes the DB's `ck_classes_seats_not_oversold` reject the sweep loudly rather than hiding the drift.
- **Never waits on a hold row** (`SKIP LOCKED`): a row another request holds is being dealt with by that request. The class row is updated only after `per_class` has consumed every flipped row, so the sweep never holds the class lock while still locking hold rows.
- **One sweep at a time** across all API instances, via `pg_try_advisory_xact_lock` taken inside the transaction (released at commit/rollback, so a crash cannot leave it behind). A sweep that does not get the lock skips; the holder is doing the same work. This also removes any class-row lock-order question between two sweeps.
- A backlog larger than one batch is drained by looping until a batch comes back short.
- Confirmed and cancelled holds are never touched, whatever their `ExpiresAt`.

**Why hold creation does not use `SKIP LOCKED` (and the sweep does).** If a request skipped rows that a sweep had locked but not yet released, it could claim a seat while the sweep's decrement was still uncommitted and see a false NO_SEAT_AVAILABLE for a seat that has in fact expired. So hold creation waits for those rows (correct counters once it proceeds), which is why its cleanup must lock in a fixed order (next point). The sweep has no such concern: skipping a row only means it is cleaned up a moment later.

**Correction to Session 3: the hold-creation cleanup could deadlock.** Session 3 stated "no deadlocks". The race test written for this session disproved it: when many `POST /classes/{id}/holds` requests reach a class with a pile of expired-but-unswept holds, each runs the step-1 cleanup over the same rows, and each keeps every row it touches locked until commit, in whatever order its scan meets them, so two requests can end up holding each other's next row. Postgres reported `40P01 deadlock detected` ("while locking tuple ... in relation holds") and the loser got HTTP 500, which the project forbids for a predictable situation. It reproduced with **no sweep running at all** (in two 40-round stress runs with sweeps off, 29 and 27 requests failed). Fix, in `HoldService.CreateAsync` step 1: the rows are locked in one fixed order (`SELECT "Id" ... ORDER BY "Id" FOR UPDATE` in a `MATERIALIZED` CTE, so no request can hold a row another wants while wanting one it holds), and the class row is updated only after a `count(*)` over all flipped rows, so it is never locked while hold rows are still being locked. Only the lock order changed: the same rows flip and the counter drops by the same amount. After the fix the same race (with and without concurrent sweeps) ran clean repeatedly (0 deadlocks in 5 repeated runs plus the full suite), against failures on every pre-fix run. Tests: `Concurrent_hold_requests_cleaning_up_the_same_expired_holds_never_fail` and `Sweep_racing_hold_creation_keeps_counters_equal_to_the_rows`. Lock order overall is now: hold rows in Id order, then the class row; confirm/cancel (one hold row, then the class row) and the sweep (skips locked rows, then class rows) fit that order.

**Test data must respect the counter invariant.** The sweep is global, so it also reaches rows seeded by other tests in the shared database. One Session 2 test seeded HELD rows (one expired) without moving `HeldSeats`, which the sweep then correctly refused to push below zero; that test now seeds the counters to match its rows. Its assertions (GET excludes the expired hold) are unchanged.

**GET /health.** `HealthController` -> `IHealthService`/`HealthService`, controller only maps the result. The check is `SELECT 1` through the app's own `DbContext`, bounded to 3 seconds so a hung database cannot hang the probe. 200 `{ "status": "ok", "database": "up" }`; 503 `{ "error": "DATABASE_UNAVAILABLE", "message": ... }` in the standard error shape (the exception goes to the log, not the client). A client disconnect is not reported as a database failure. No `X-Student-Id`. It is an operational endpoint outside the frozen student-facing `API_CONTRACT.md`, which is left untouched. The 503 test starts a second real Postgres container and stops it mid-test, so no mocks and the shared test database is unaffected.

**Still not built:** global exception-handling middleware (unexpected exceptions still fall to the framework default).

## Session 6 — Global exception handling, correlation id, 4xx audit

**Note:** `docs/BUSINESS_RULES.md` still does not exist, so `API_CONTRACT.md` was the only documented source for the audit. This session builds the middleware that Sessions 2 and 5 listed as "not built yet".

**Pipeline order** (`Program.cs`): `CorrelationIdMiddleware` -> `UseSerilogRequestLogging` -> `ExceptionHandlingMiddleware` -> `UseStatusCodePages` -> Swagger -> controllers. The correlation id is outermost so the request-log line carries it; the exception handler sits inside request logging so that line records the status the client really received.

**Exception handling** (`Api/Middleware`). `ExceptionHandlingMiddleware` catches anything that escapes a controller or service, logs the real exception, and answers `{ "error", "message" }` with a 4xx. Controllers keep answering predictable failures themselves; this is the backstop. The decision of status/code lives in one pure function, `ExceptionMapper.Map`, which looks through wrapper exceptions (`DbUpdateException`, `AggregateException`, EF's retry wrapper `InvalidOperationException`) to the one that matters:

| Exception | Status / code |
|---|---|
| `PostgresException` 40001, 40P01, 55P03 or class 23 (serialization, deadlock, lock timeout, unique/FK/check) | 409 `CONFLICT` (caller can retry) |
| `PostgresException` class 22 (data exception: NUL byte, out-of-range value, ...) | 400 `INVALID_INPUT` |
| `BadHttpRequestException` | its own 4xx (non-4xx coerced to 400): 408 `REQUEST_TIMEOUT`, 413 `PAYLOAD_TOO_LARGE`, else 400 `BAD_REQUEST` |
| client disconnected (`RequestAborted` + `OperationCanceledException`) | logged at Information, status 499, no body; not an error |
| anything else | **400 `UNEXPECTED_ERROR`** |

- **Why 400 for the catch-all.** `CLAUDE.md` says the global handler "still returns a 4xx-shaped error", and a failure is never a 5xx. 400 is the generic 4xx; it is one constant in `ExceptionMapper` if a different status is preferred. This includes "database unreachable" on student-facing endpoints. `GET /health` keeps its Session 5 `503 DATABASE_UNAVAILABLE`: it is an operational probe outside the student contract, and its own handler already answers in the standard shape.
- **Nothing from the exception reaches the client.** Messages are fixed text; no exception message, type name, SQL or stack frames. This holds in Development too (the framework's developer exception page never sees the exception because this middleware handles it first). Tests assert a secret string in the exception text is absent from the response and present in the log.
- **If the response has already started** the status line is gone and an error body is impossible: the failure is logged at the mapped level, then `HttpContext.Abort()` so the client sees a failed response rather than a truncated one that looks complete.
- **Correlation id.** `X-Correlation-Id` from the caller is used if it matches `^[A-Za-z0-9._-]{1,64}$`, otherwise a fresh GUID (`N` format) is generated; anything else is replaced, since the value is echoed into a header and into logs. The id is set as a response header on every response (via `OnStarting`, so it survives the handler clearing a half-built response), and pushed into Serilog's `LogContext` as `CorrelationId`, so every event written during the request carries it. The console sink now uses an output template with `{Properties:j}` so the property is visible (the default template hides properties). For `UNEXPECTED_ERROR` the id is also in the message (`... Reference: <id>`), so a client report maps straight to the log lines. The error body stays exactly `{ "error", "message" }`; no extra field.

**Framework-generated 4xx now use the standard shape too.** Unknown route, wrong method and wrong content type used to come back as an empty body or `application/problem+json`. `SuppressMapClientErrors = true` stops MVC converting bare 4xx results to ProblemDetails, and `UseStatusCodePages` fills any bodiless 4xx using `HttpErrors.ForStatus`: 404 `ROUTE_NOT_FOUND`, 405 `METHOD_NOT_ALLOWED` (the `Allow` header is kept), 415 `UNSUPPORTED_MEDIA_TYPE` (also a POST with no body or content type), 406 `NOT_ACCEPTABLE`, otherwise `REQUEST_REJECTED`. Responses that already have a body (every controller error) are untouched.

**Audit of `API_CONTRACT.md` 4xx cases.** `ContractErrorCodesTests` provokes every documented case through the real endpoint and asserts the exact status, the stable error code, JSON content type and exactly the two fields `error` and `message`. 35 test rows: 34 error responses plus the idempotent owner re-confirm that must stay 200. They cover every endpoint that has a documented or implied 4xx (all except `GET /classes`, which has none), including the header-before-class-lookup order on `POST /classes/{id}/holds` and the non-owner never getting the idempotent 200 on confirm. Note the contract itself documents the 400 only for `POST /classes/{id}/holds`; the same `INVALID_STUDENT_ID` 400 on confirm, delete and `/me/holds` and the 400 `VALIDATION_ERROR` on `POST /classes` are implied by the header rule and Session 2, and are asserted too. **All of them already returned the expected status and code before this session**; no controller or service logic changed. Two real defects were found and fixed:
1. `POST /classes` with a NUL (`\u0000`) in `name` passed validation, PostgreSQL refused to store it, and the client got a **500 with a stack trace**. The validator now rejects it with 400 `VALIDATION_ERROR`, and the mapper's class-22 rule is the backstop for any other value the database refuses.
2. The framework-generated 4xx described above did not use the error shape.

**Known and left as is.**
- Kestrel rejects some requests before any middleware runs (a `%00` in the URL path, a malformed request line, oversized headers). Those get Kestrel's own bare 400/431 with no body; no middleware can shape them.
- Model-binding 400s (`VALIDATION_ERROR`) still carry the framework's wording for JSON type errors, e.g. a mention of the DTO type name. The status, code and shape are right; the text is pre-existing from Session 2.

**Testing approach.** The handler is exercised through the full pipeline in the Development environment. The thing that throws is a test double for `IClassService`; everything between it and the client is the application's real code. Log assertions use a Serilog `ILogEventSink` registered in the test host's DI (picked up by `ReadFrom.Services`), so they check what Serilog actually receives. A separate smoke run against real Kestrel and a real Postgres that was stopped mid-run confirmed the 4xx body, the response header and the ERR log line carrying the same id.

## Session 7 — Docker

No application code changed. Run it with `docker compose up --build` (API on http://localhost:8080, Swagger at `/swagger`, probe at `/health`); `docker compose down` keeps the data, `docker compose down -v` deletes it.

- **Dockerfile lives at `src/Api/Dockerfile`, build context is the repo root.** Api references Domain and Infrastructure, so the context must include `src/`. Compose sets `context: .` and `dockerfile: src/Api/Dockerfile`. Restore runs on the three csproj files alone (test projects are not copied), so the package layer is cached until a package reference changes.
- **Alpine runtime (`aspnet:8.0-alpine`) and non-root.** Small (176 MB image), ships an unprivileged `app` user (uid 1654, used via `USER app`) and has busybox `wget`, which the `HEALTHCHECK` needs; the Debian runtime image has no curl or wget. Kestrel listens on 8080 (`ASPNETCORE_HTTP_PORTS`), since a non-root user cannot bind below 1024. Alpine runs .NET in invariant-globalization mode (no ICU); the API and Npgsql need no culture data and the whole flow was exercised in the container, but revisit this if culture-specific behaviour is ever added.
- **Production environment inside the container.** `ASPNETCORE_ENVIRONMENT=Production`, so `appsettings.Development.json` (a localhost connection string) is never loaded and the connection string can only come from `ConnectionStrings__Postgres`; a missing value still fails fast at startup (Session 1). Swagger is enabled unconditionally in `Program.cs`, so `/swagger` is also served in the container; left as is.
- **Connection string is assembled in `docker-compose.yml` from `POSTGRES_DB`/`POSTGRES_USER`/`POSTGRES_PASSWORD`**, so the database and the API cannot disagree about credentials. The host name is the compose service name `postgres`. Consequence: a `;` in the password would break the connection string (noted in `.env.example`).
- **Defaults in compose, documentation in `.env.example`.** Every variable has a `${VAR:-default}` in the compose file, so `up --build` works with no `.env`; `.env.example` lists them all with the same values for people who want to override. `.env` is git-ignored and also excluded from the build context. `POSTGRES_*` only take effect when Postgres first creates its volume; changing them afterwards needs `docker compose down -v`.
- **Start order and health.** `api` waits for Postgres' `pg_isready` healthcheck (`condition: service_healthy`), then migrates and serves (migrations still run at startup, Session 1). The API healthcheck calls `GET /health`, which is 503 when the database is down, so the container then reports `unhealthy`. Docker does not restart on that alone; `restart: unless-stopped` only reacts to the process exiting.
- **Postgres is not published to the host.** Only the API needs it, and it avoids clashing with a local Postgres on 5432. `docker compose exec postgres psql ...` for inspection; a commented line in the compose file shows how to publish it. Data lives in the named volume `school-admission_postgres_data`.
- **Plain HTTP only.** There is no TLS termination; put a reverse proxy in front for anything beyond local use.

## Session 8 — Unit and integration tests for the business rules

No production code changed. `docs/BUSINESS_RULES.md` still does not exist, so the rules came from `API_CONTRACT.md` and the Session 3-4 interpretations (rule 2 expiry, rule 3 one active hold per class, rule 5 idempotent confirm). Rules 1 (concurrency) and 6 (restart persistence) were excluded by instruction, and nothing in the repo defines a rule 4.

- **The services are not unit-tested against a mocked database.** `HoldService` and `ClassService` are SQL (the atomic `UPDATE`/CTE statements of Sessions 3-5), and a mock or an in-memory provider would not execute that SQL, so a test against one would prove nothing about it. They are tested as the real classes on the real Postgres container instead, with the two things that matter injected: the clock and the hold duration. What can be unit-tested without a database is, in `UnitTests`: the domain rule (`Hold.EffectiveStatus`), the options, the validator, and the controllers, which are tested against hand-written doubles of `IHoldService`/`IClassService` that also record their calls (so a test can show the service was *not* reached). No mocking library was added; the existing tests already use hand-written doubles.
- **`FakeClock` + `ServiceHarness` (IntegrationTests).** `FakeClock` is a `TimeProvider` the test advances by hand; `ServiceHarness` builds `HoldService`/`ClassService` per call in a fresh DI scope (as a request would) with that clock and a chosen `HoldOptions.DurationSeconds`. This is what makes the expiry boundary exact (a hold is HELD one millisecond before `ExpiresAt` and EXPIRED at it) with no sleeping. Exactly one test uses real time (`With_a_short_HOLD_DURATION_SECONDS_the_seat_really_does_come_back_in_wall_clock_time`, 4 s, over real HTTP with the sweep off): the fake clock cannot show that the real `TimeProvider.System` wiring and the configured duration reach the endpoints.
- **Test data stays out of other tests' way.** The fake clock starts at the real current time cut to a whole second (Postgres keeps microseconds, so whole seconds compare exactly), and only moves forward, so a hold's stored `ExpiresAt` is in the real future and the global expiry sweep that other tests run never reaches it. ## Session 9 — Concurrency tests (rule 1), single process and two processes

No production code changed; `ApiFactory` only gained a `ConnectionString` property. `docs/BUSINESS_RULES.md` still does not exist, so "rule 1" is the Session 3 reading: *seats are never oversold (held + confirmed <= total)*. Sessions 3-5 already had concurrent tests, but they only looked at the final state. These add the two things the requirement asks for: the database is watched *while* the race runs, and the same race is run against two separate API processes.

**The race (`SeatRace`, shared by both test classes).** One class, `S` seats, `N` requests with `N >> S`, one distinct student per request. All requests are parked on a start gate and released together, so they collide instead of trickling in. Asserted, for every race: every response is 201 or 409 (no 5xx, no dropped connection); exactly `S` are 201 and exactly `N - S` are 409; every 409 is `NO_SEAT_AVAILABLE` (students are distinct, so any other 409 code would mean a bug, and `CONFLICT` would mean the database refused something the code should have refused first); the `S` winners hold `S` distinct `h_` ids; the final state is `S` seats taken, `S` active hold rows and `S` rows in total (refused requests leave nothing behind). The peak number of requests in flight must be at least 2, so a test that accidentally ran serially cannot pass as a concurrency test.

**"Never exceeded at any point" is checked two ways, because sampling alone cannot prove it.**
- *Sampler.* A separate connection (its own pool, `ApplicationName=seat-race-sampler`, so it never takes a connection the API needs) runs one SQL statement over and over for the whole race and once after the last response: `HeldSeats`, `ConfirmedSeats`, the count of HELD/CONFIRMED rows and the count of all rows for the class. One statement is one snapshot, so the counters and the rows are seen together. Every sample must satisfy `held + confirmed <= S`, `active rows <= S`, and `held + confirmed == active rows` (the counters and the rows are written in one transaction, so no snapshot may show one without the other). The test also requires at least one sample taken while requests were running; a typical 5-seat, 50-request run takes 110-250 samples. A sample is evidence about the instants it hits, not about every instant.
- *The constraint.* What makes the claim hold at every instant is that PostgreSQL refuses the bad state outright. `The_database_itself_refuses_a_state_with_more_seats_taken_than_exist` sets the counters to (4,0), (0,4), (2,2) and (3,1) on a 3-seat class and asserts SQLSTATE 23514 on `ck_classes_seats_not_oversold` each time. That constraint was added in Session 3 but nothing tested it directly until now.

**Single process (`SeatRaceTests`, `ApiFactory`'s Postgres container, in-memory TestServer).** 5 seats / 50 requests (the assignment's scenario), 1 seat / 30 requests (every request fights over the last seat), and the 5/50 race repeated on 15 fresh classes, since one race won by luck is not evidence.

**Two processes (`MultiProcessSeatRaceTests`, `TwoApiInstancesFixture`, `ApiProcess`).** Two real OS processes, `dotnet Api.dll`, each on its own free port on 127.0.0.1, both pointed at one Postgres container the fixture starts for itself. Nothing is shared between them or with the test host except the network and the database: no memory, connection pool or DI container. Request `i` goes to instance `i % 2`, so half of the requests hit each process in the same instant. The same assertions apply to the combined result, and in addition: the two instances have different PIDs and ports and neither is the test host; a class written through A is readable through B; and every winning hold, written by one process, is read back through the *other* one. The tests are 5/50, 1/40 and 5/50 repeated on 10 fresh classes. The seats really do split between the processes (observed 3/2, 4/1, 1/4 ... per race), so both were admitting students at the same time. Details:
- The environment is what the Docker deployment passes: `ConnectionStrings__Postgres`, `ASPNETCORE_URLS`, `ASPNETCORE_ENVIRONMENT=Production`. Hold duration and the expiry sweep are left at their defaults, so both processes also run the background sweep, as in production.
- **Started one after the other**, each waited on `GET /health`. The first one applies the migrations at startup; the second finds them applied. Starting both at once on an empty database would race two migrations, which is a startup concern the API does not guard against (EF Core 8 takes no migration lock on Npgsql) and not what these tests are about.
- `Api.dll` is the Api project's own build output (`src/Api/bin/<configuration>/<framework>/`), found from the test assembly's location; it exists because the test project references the Api project. The process's stdout and stderr are always drained (a full pipe would stall the server) and the last 60 lines are put in the failure message if an instance dies or never becomes healthy. Both processes are killed, with their children, when the fixture is disposed.
- The class is in the `api` collection although it does not use that collection's `ApiFactory` or database: this only stops it overlapping the other integration tests, which compete for the CPU and include timing-sensitive ones. The first race against freshly started processes is several times slower than later ones (JIT); that is not a failure.

**Tests were checked against deliberate bugs**, in a throwaway copy of the repo so the real tree was never changed:
- *Guard removed from the seat-claim `UPDATE` (the database `CHECK` kept):* the database still refused every oversell, so no seat was sold twice, but the losing requests were refused by the constraint (409 `CONFLICT`, via the Session 6 mapper) instead of by the code (409 `NO_SEAT_AVAILABLE`). Both `SeatRaceTests` races failed on that code. This is the defence in depth working, and the test noticing that the first line of defence was gone.
- *Guard removed and the `CHECK` relaxed to no upper bound (a real oversell):* all three race tests run (5/50 and 1/30 in-process, 5/50 over two processes) failed with `expected exactly 5 x 201 but got 50` and the sampler reporting 50 seats taken at once against a limit of 5.

**Known limits.** They need Docker (as every integration test does) and a built Api project. The free port is found by binding port 0 and releasing it, so another program could in theory take it before the instance binds; it would show up as an instance that never becomes healthy, with its output in the failure message. The in-process tests use TestServer (no TCP), which is why the two-process tests exist. These tests prove the correctness invariant, not throughput. `ApiFactory` still uses the parameterless `PostgreSqlBuilder()`, which Testcontainers marks obsolete (a build warning); the new fixture uses the image constructor.

## Session 16 — CORS, so the browser frontend can call the API

Production code changed only in `Program.cs` (the wiring and one startup log line) plus the new `Api/Cors/` folder. No endpoint, status code, error code or field changed, so `docs/API_CONTRACT.md` is untouched and the OpenAPI document is unaffected. `ExceptionHandlingMiddleware` was **not** changed (see "A suspected trap" below).

**Why.** The frontend is a page served from its own origin (the Vite dev server on `http://localhost:5173`, later its own container) and calls `http://localhost:8080`. A browser discards the response of a cross-origin call unless the API sends `Access-Control-Allow-Origin`, and the API sent no `Access-Control-*` header at all (`grep -ri cors backend/src` found nothing). Measured before the change, in a real browser from `http://localhost:5173` against the running API: **every call was blocked with `TypeError: Failed to fetch`, including a plain `GET /classes`** that `curl` showed was answered fine, and a preflight `OPTIONS` got a bare `405 METHOD_NOT_ALLOWED` with no CORS headers. The frontend's axios interceptor (Session 12) adds `X-Student-Id` to every request, which is not a header a browser sends without asking first, so **every endpoint, GETs included, is preflighted**, not only the four that require the header.

**The policy** (`Api/Cors/CorsSetup.cs`): one default policy for all endpoints, limited to what the frontend uses.
- *Origins:* an exact allow-list (below).
- *Methods:* `GET`, `POST`, `DELETE`, the three the contract uses.
- *Request headers:* `Content-Type` and `X-Student-Id`. A preflight asking for anything else (tested with `x-evil`) is not approved.
- *Exposed response header:* `X-Correlation-Id`. The `UNEXPECTED_ERROR` message tells people to quote that id, and a page cannot read the header unless it is exposed.
- *Preflight cache:* `Access-Control-Max-Age` 600 s, so the 3 to 5 s polling does not pay a preflight round trip on every refresh. Browsers apply caps of their own, so this is an upper bound, not a promise.
- *No credentials.* Identity is a header, not a cookie, so `Access-Control-Allow-Credentials` is never sent.

**Where it sits in the pipeline** (`Program.cs`): `CorrelationId` -> request logging -> **`UseCors`** -> `ExceptionHandlingMiddleware` -> status-code pages -> Swagger -> controllers. Inside request logging so preflights are logged with their correlation id; outside the exception handler so a preflight is answered with `204` by the CORS layer and never reaches a controller or the database, and so every response, errors included, carries the CORS headers. That last point matters because the frontend shows the `message` of every 4xx: without the allow-origin header the browser hides the body and the page sees only a failed network request. Tests cover a controller 4xx (`INVALID_STUDENT_ID`), the framework's own 404 and 405, and an unexpected exception.

**A suspected trap that turned out not to be real.** `ExceptionHandlingMiddleware` calls `Response.Headers.Clear()` before writing an error, so the CORS headers set earlier looked likely to be wiped on an unexpected error, leaving an `UNEXPECTED_ERROR` the browser cannot read. The test for exactly that (`An_unexpected_error_is_readable_by_the_frontend_and_still_carries_the_correlation_id`) was written first and **passed with no production change**: the response was a `400 UNEXPECTED_ERROR` (so the handler and its `Clear()` did run) and still carried `Access-Control-Allow-Origin`, `Vary: Origin` and `X-Correlation-Id`. So on this ASP.NET Core 8 the CORS headers evidently survive (observed, not read from the framework source). The same test failed while CORS was absent, so it does detect missing headers on that path. The handler was left alone, since changing it without a failing test would have been guesswork, and the test stays as a guard in case a framework upgrade or a change to the handler breaks it.

**Configuration: `CORS_ALLOWED_ORIGINS`** (`Api/Cors/ApiCorsOptions.cs`).
- *Not set:* `http://localhost:5173` and `http://localhost:4173` (`npm run dev` and `npm run preview`), so the frontend works with no configuration.
- *Set but blank:* no origin at all, i.e. CORS off, for a deployment where the API and the frontend share one origin. It deliberately does **not** fall back to the defaults, otherwise there would be no way to turn it off.
- *Otherwise:* a comma-separated list, trimmed, empty items ignored, duplicates collapsed. Each entry is written the way a browser writes an `Origin` header (lower-case, no default port, no trailing slash), because the middleware compares plain strings: `HTTP://LOCALHOST:5173/` is stored as `http://localhost:5173`.
- *Refused at startup,* with a message naming the setting and the offending value: `*`, `null` (the origin of sandboxed iframes and `file://` pages), a missing scheme, anything but `http` or `https`, a path, a query, a fragment, credentials, or garbage. A mistyped origin would otherwise be indistinguishable from "the browser blocks everything", which is very hard to trace back to one setting. The check runs in `Program.cs` before the host is built, so it ends up in the same `Fatal` log line as any other startup failure.
- *Why an exact list and no wildcard:* CORS is not access control (anyone can already call the API with `curl`; see ASSUMPTIONS.md, 24), so this is about being deliberate about which pages a browser will let read the API, not about secrecy. The accepted values are logged at startup (`CORS allows browser origins [...]`, or `CORS is off`).
- *Adding the frontend container later:* put its origin in `CORS_ALLOWED_ORIGINS` (in `.env`, or in the compose file's default). The frontend's `apiBaseUrl` stays a browser-reachable URL, `http://localhost:8080` (Session 11).

**Compose.** `docker-compose.yml` passes `CORS_ALLOWED_ORIGINS: "${CORS_ALLOWED_ORIGINS-http://localhost:5173,http://localhost:4173}"`. The form is `-`, not `:-` like the other variables: `-` applies the default only when the variable is **unset**, so an empty value in `.env` stays empty and really means "off". Checked with `docker compose config`: unset gives the two defaults, `CORS_ALLOWED_ORIGINS=` gives `""`, a custom list passes through unchanged.

**How it was built (tests first).**
- *Integration, `CorsTests` (24):* the preflight for every call the frontend makes (10 method/header combinations, answered `204`, no body); a disallowed origin, a method the API does not offer and an unlisted header are not approved; allow-origin, `Vary: Origin` and the exposed correlation id on a real response; a request with no `Origin` gets no CORS headers; the error cases above; and the setting itself (a custom list replaces the defaults, blank turns CORS off while the API keeps working, `*` stops the host from starting with a message naming `CORS_ALLOWED_ORIGINS`).
- *Unit, `ApiCorsOptionsTests` (25):* the rules for the value above.
- *Two RED attempts were discarded.* The first run of the integration tests failed all 21 tests with `DockerApiException ... InternalServerError` while Testcontainers tried to start its helper container on an overloaded machine. That says nothing about CORS, so no production code was written on it. The valid RED came once Docker could start containers again: 21 tests, 16 failing on real assertions (for example `204` expected and `405` received, or no `Access-Control-Allow-Origin`), and the 5 that passed were the "must not be approved" guards, which pass trivially before any CORS exists. ### Runtime config: `window.__APP_CONFIG__`, not `import.meta.env`

The backend base URL is read from `window.__APP_CONFIG__.apiBaseUrl`, which `frontend/public/config.js` sets (`window.__APP_CONFIG__ = { apiBaseUrl: "http://localhost:8080" }`). `index.html` loads it with a classic `<script src="/config.js">` in `<head>`, ahead of the app's `<script type="module">`. Module scripts are deferred and classic ones block, so the config is guaranteed to exist before any app code runs.

**Why not `import.meta.env.VITE_API_BASE_URL`.** Vite replaces `import.meta.env.*` with literal values *while building*, so the URL ends up inside the JavaScript bundle. Changing the backend address would then mean rebuilding the image, and one image could not move between environments. `docs/FRONTEND_SPEC.md` requires the URL to be resolvable at container runtime. `config.js` lives in `public/`, which Vite copies to `dist/` byte for byte without processing, so whoever starts the container can overwrite that one file and the same bundle talks to a different backend.

**How it is read** (`src/config.ts`, `src/api/client.ts`). The axios instance has a request interceptor that sets `baseURL = getApiBaseUrl()` on every request, so it is never captured at import time or at build time. `getApiBaseUrl()` trims the value and strips trailing slashes, and **throws a descriptive error** if the value is missing or blank (for example `/config.js` was not served, or a static server answered it with the `index.html` fallback, which is a syntax error that leaves `__APP_CONFIG__` unset). Because it throws inside the interceptor, the failure is a rejected request with a readable message that TanStack Query can surface, not a crash at import time that leaves a blank page.

**Checked, not assumed.** A production build with the client imported contains the string `__APP_CONFIG__` and no `localhost:8080` anywhere, and `dist/config.js` is identical to `public/config.js`. In a browser against the dev server, the instance resolved `http://localhost:8080/classes` from `config.js`, then `http://api.example.test:9999/classes` after `window.__APP_CONFIG__` was changed at runtime (trailing slash stripped), and rejected with the error above for a blank value and for a deleted config.

**Not built yet (the frontend Docker session).** Overwriting `config.js` at container start (for example an entrypoint that writes it from an `API_BASE_URL` variable) and serving it with `Cache-Control: no-cache` so a changed value is not hidden by a stale cached copy. `config.js` also holds a plain default for `npm run dev`.

**Correction to the repository-layout note above.** It says a future frontend service could reach the backend as `http://backend:8080`. That is wrong for this app: the API calls are made by the *browser*, not by the frontend container, and a browser on the host cannot resolve the compose service name `backend`. `apiBaseUrl` must be a URL the user's browser can reach, which under `docker compose` is the published port, `http://localhost:8080` (`API_PORT`).

### Open item: the backend has no CORS configuration

`grep -ri cors backend/src` finds nothing, so the API sends no `Access-Control-Allow-*` headers. The frontend is served from its own origin (the Vite dev server on `http://localhost:5173`, later the frontend container) and calls `http://localhost:8080`, which a browser treats as cross-origin and will block. The `X-Student-Id` header and the JSON `Content-Type` also force a preflight `OPTIONS` request on every call. **This session did not change the backend** (out of scope) **and no request to the real API was made**, so nothing here has been tried against it. It has to be settled before the first real screen works, by either of:
- adding CORS to the API (allow the frontend origin(s); methods including `DELETE`; headers `X-Student-Id` and `Content-Type`), or
- serving the frontend and the API from one origin behind a reverse proxy. `getApiBaseUrl()` currently rejects an empty string, so that option would also need it to accept a relative base such as `/api`.

**Resolved by Session 16 (backend):** the API now sends CORS headers for the origins in `CORS_ALLOWED_ORIGINS` (default `http://localhost:5173` and `http://localhost:4173`); see "Session 16" under Backend decisions. The first option was taken, so the same-origin proxy and the `getApiBaseUrl()` change are not needed for now.

## Session 12 — Student identity (`studentId` context, header input, `X-Student-Id` interceptor)

Scope: who the student is, kept in one place and sent with every request. No screens, no error mapping, no error boundary (later sessions).

### One owner for the value: a small store, exposed as a React context

`src/identity/studentIdStore.ts` owns the id: it validates, keeps it in memory, persists it to `localStorage["studentId"]` and notifies subscribers. `src/identity/StudentIdProvider.tsx` is the React context over it (`useSyncExternalStore`), giving components `{ studentId, setStudentId }` through `useStudentId()`. The axios interceptor reads the same store with `getStudentId()`.

**Why a store behind the context, not plain `useState` in the provider.** An axios interceptor lives outside React and cannot call `useContext`. Handing the value from React state to the interceptor in an effect would leave a window in which a request made during the first commit (or by a child's layout effect, which runs before the parent's) sees no id. With one store both sides read the same value at the same instant, and the request that follows a Save already carries the new id. The load from `localStorage` happens on the first read, which is the first render, so a returning student never sees an empty input flash.

### What is accepted
- **Exactly 17 ASCII digits**, `^[0-9]{17}$`, matching the backend's rule. In JavaScript `$` (no `m` flag) matches only at the very end, so the trailing-newline gap noted for the .NET pattern in Session 8 does not exist here. Surrounding whitespace is trimmed first (a copy-paste artefact); whitespace inside the number is rejected. Bangla digits are rejected too, as the backend would: the inline error says "(0-9)". There is deliberately no `maxLength` on the input, since silently truncating a pasted 18-digit value to 17 would accept a wrong number.
- Anything else shows an inline error (`role="alert"`, `aria-invalid`) and changes **nothing**: not the stored value, not the id used for requests. A previously saved id stays in force until a valid replacement is saved.
- A value read from `localStorage` that is not 17 digits (hand-edited, from another version) is **ignored**, not sent, and left in place until a valid id overwrites it.

### The interceptor (`src/api/client.ts`)
A second request interceptor sets `X-Student-Id` from `getStudentId()` on every request, read at send time. With no id entered, **no header is sent** (not an empty one); the endpoints that need it answer 400 `INVALID_STUDENT_ID` (the backend's code for a missing or malformed header), which the error-handling session maps to a message. It sends the id on every call, including `GET /classes`, which does not need it: harmless to the backend, and it keeps the rule "every request" free of exceptions. The unsaved text in the input is never sent, only the accepted id.

**`asStudent` and the `studentId` parameters of `createHold`, `confirmHold`, `cancelHold` and `listMyHolds` were removed.** Two ways to set the same header would let them disagree, and nothing used them yet. Screens call `createHold(classId)`, `listMyHolds()` and so on.

### Header on every page (`src/components/AppLayout.tsx`)
`AppLayout` wraps `<Routes>` inside `BrowserRouter` (rather than being a layout route), so the header, with its input, is rendered on every URL **including ones that match no route**. It is one component instance for the whole session, so an unsaved draft survives navigation. The page content is in `<main>`; the app title links to `/`. Styling is one small CSS file next to the component; the rest of the app is still unstyled.

### Failure handling
Every `localStorage` access is in `try/catch` (blocked site data, private windows, quota). If a write fails the id stays in memory and is still sent for the rest of the page load; it just will not survive a reload. For that reason the confirmation text says "Registration number set.", not "saved on this device". Checked with `Storage.prototype.setItem` made to throw: no uncaught error, id accepted, header sent.

### Not done, on purpose
- **No cross-tab sync** (no `storage` event listener). A change made in another tab is picked up on reload; until then this tab keeps sending the id it shows.
- **No "clear / sign out"** control; the spec has no login. Saving a different valid number replaces the old one.
- **No automated tests.** The frontend has no test runner (Session 11) and adding one was outside this session. The behaviour was checked by hand in a browser (see PROGRESS.md).
- **CORS is still open** (Session 11 item). One consequence to note: `GET /classes` used to be a "simple" cross-origin request, but now that it carries `X-Student-Id` once an id is entered, every call is preflighted, so the backend's CORS policy must allow that header for all of them.

### For the screens that follow
- Do not fire an id-requiring query before an id exists: use `enabled: studentId !== null` (from `useStudentId()`), otherwise the first call is a guaranteed 400.
- **Put `studentId` in the query key** of anything that depends on it (`/me/holds`, a hold read as its owner). The header changes when the id changes, but TanStack Query only refetches when the key changes; without it a student switching numbers would briefly see the previous student's cached applications.

## Session 13 — Class list screen (polling `GET /classes`)

Scope: the `/` screen only. The apply button is not wired to the API (apply flow, Session F4); the error text helper is local to this screen (error handling, later).

### Polling policy: 4 s interval, no retry
`useClassList()` uses `refetchInterval: 4000` (the spec says 3-5 s) and `retry: false`. TanStack's default is three retries with backoff, about 7 s before a first-load error would appear. Here the next poll is the retry: an outage is shown after the first failed request and the screen recovers by itself when a poll succeeds. `refetchIntervalInBackground` is left at its default (off): polling pauses while the tab is hidden and a refetch fires when it is visible again, so nothing hammers the backend for a page nobody is looking at. A window that is merely unfocused but visible keeps polling.

### "Spinner on first load only" needs more than `isPending`
In TanStack Query v5, `fetchState()` (query-core `query.ts`) sets `status: 'pending'` and `error: null` whenever a fetch starts and the query has no data. After a failed first load, every poll would therefore switch the screen error -> loading -> error, the same full-page flicker the first-load-only spinner is meant to avoid (the library's source was read, not assumed). The hook keeps the last error in state until a request succeeds, and treats "failed at least once and not succeeded since" (`errorUpdateCount > 0 && !isSuccess`) as an error even while the retrying request is in flight. Once there is data, `status` stays `error` between polls on its own, so that case needed nothing extra. Observed in a browser: one loading -> error transition, then no further change across seven failing polls.

### Three states, one union
`useClassList()` returns `loading` (first request only), `error` (no data yet) or `ready` (data, plus `refreshError` when the latest refresh failed). With data on screen a failed refresh keeps the last numbers and shows a banner saying they may be out of date, rather than replacing a usable table with an error. A stale seat count is still better than none because the backend decides a hold's outcome anyway (409 if the seat is gone).

### Query key and the student id
The key is `["classes"]`, with no student id: the response is the same for everyone. The interceptor still sends `X-Student-Id` once one is entered (Session 12), which the backend ignores here. The key is exported (`classListQueryKey`) so the create-class and apply screens can invalidate it for an immediate refresh instead of waiting up to 4 s.

### Disabled rule and the Full tag
The button is disabled when `availableSeats <= 0` (the spec says `=== 0`; the backend's CHECK keeps it from going negative, so `<=` only guards against a bad value). A disabled button gives no reason by itself, so a "Full" tag is shown next to the 0.

### Layout
A real `<table>` (column headers, row header = class name, caption and the apply column header visually hidden). Each button has `aria-label="আবেদন করুন: <class name>"` so screen readers can tell the identical buttons apart. Narrow screens scroll the table inside its own box; the last column is `position: sticky; right: 0` with `background: Canvas` so the apply button never scrolls out of view. Colours are either inherited, set with opacity, or carry their own background, so they read on a light or a dark page (the existing header CSS still uses fixed greys that are faint on a dark page; left to the styling session).

### Not done, on purpose
- The real backend with data, from a browser: blocked by the missing CORS configuration (Session 11 open item). The failure case was exercised against it (the page shows the error), everything else against a throwaway mock.
- No automated tests: no frontend test runner exists, and adding one is outside this session.

## Session 14 — Apply flow (`POST /classes/{classId}/holds` from the class list)

Scope: the apply button only. No application status screen, no central error mapping (both later sessions).

### One mutation hook, one instance per row
`useApplyForClass()` (`src/api/useApplyForClass.ts`) wraps `createHold` in `useMutation` and owns the three side effects: navigate on 201, expose the failure, invalidate the class list. It is called in `ClassRow`, not once in the page, so every class has its own `isPending` and `error`. A failure on class A does not clear or replace a message on class B, and only the clicked button is disabled. The hook-level callbacks (not per-call `mutate(..., { onSuccess })` ones) are used so the navigation still happens if the row re-renders or unmounts while the request is in flight.

### Success navigates, failure never does
201: `navigate("/holds/" + encodeURIComponent(hold.holdId))`, using the id the backend returned and nothing else. Any failure (409 no seat, 409 already applied, 404, 400, network) leaves the student on the list. `retry` stays at the mutation default of 0: re-sending a POST that creates a seat hold is not something to do behind the user's back (the backend would answer a repeat with 409 anyway).

### The message is the backend's, not ours
The inline text is `error.response.data.message` verbatim. There is deliberately no code-to-text table here: the contract's codes in `FRONTEND_SPEC.md` (`SEAT_UNAVAILABLE`, `DUPLICATE_APPLICATION`) are not the ones the backend sends (`NO_SEAT_AVAILABLE`, `DUPLICATE_ACTIVE_HOLD`), so a table written from the spec would silently never match. The backend's messages are English; if Bangla is wanted, the error-handling session should map the real codes. With no backend message (server unreachable, a non-JSON failure) the row shows the spec's generic Bangla line plus the detail the screen already computes. The message sits in its own `<tr>` under the class so it is clear which class it is about; it stays until that row's next attempt (`mutate` clears the error when a new request starts).

### Invalidate on success *and* failure
`onSettled` invalidates `["classes"]`. After a failed apply the list that was on screen is evidently out of date (typically "no seat" against a row that still showed seats), so refreshing it at once turns the row to Full instead of leaving a live button for up to 4 s. Seen in the browser: 409, then `GET /classes` immediately, then the row flipped to Full 561 ms later.

**What happens on success, and why it is a one-request flash.** `useClassList` passes TanStack's abort `signal` to the request. When the apply succeeds the page navigates away, which unmounts the only observer of `["classes"]`; TanStack then cancels the in-flight refetch that the invalidation started and reverts to the previous data, keeping the query marked invalid. So nothing is lost (the list refetches when the student returns; the default `staleTime` of 0 would do that anyway) but for one request the list shows the old seat count (seen: 5 available, then 4). Not changed, because both fixes are bigger than this session: awaiting the invalidation before navigating (costs one round trip of latency on every apply), or writing the new counts into the cache optimistically (a guess the server then corrects). Not passing `signal` in `useClassList` would also let the refetch finish in the background, but that hook belongs to the polling session and the cancellation is what stops requests for a page nobody is looking at.

### Layout of the message row
A full-width cell (`colSpan={6}`) is the row's last child, so it would inherit the pinned-last-column rule (`position: sticky; right: 0; background: Canvas`); `td.class-list-apply-error-cell` has the same specificity, comes later and resets both. The text box itself is `position: sticky; left: 0` with `max-width: calc(100vw - 3.5rem)` and normal wrapping, so on a narrow screen, where the table scrolls sideways inside its wrapper, the message stays at the left edge of the visible area. Checked at 375 px at both scroll extremes.

### Student id
The button does not check for a registration number. With none entered no `X-Student-Id` header is sent (Session 12) and the backend answers 400 with its own message, which is then shown like any other failure. Pre-disabling the button (or prompting for the number) is a UX choice for the styling or error-handling session.

### How it was checked, and what that does not cover
Against a real backend started as a separate compose project (`-p apply-verify`, port 8199, its own volume, removed afterwards), so the dev database was not written to. The backend has no committed CORS yet, so the page was served by a throwaway Vite config outside the repo (a same-origin `config.js` and a proxy of `/classes`, `/holds`, `/me`). That means the cross-origin browser-to-`:8080` path is **not** covered. Two environment notes: with the Browser pane hidden, page timers are throttled, so waits in injected scripts must not use `setTimeout`; and port 8099 was already taken by another session's API instance, so the verification stack uses 8199.

## Session 15 — Visual design system and redesign (shell and class list)

Scope: how the app looks. No behaviour changed: the identity input, the polling, the apply flow and the error states work as in Sessions 12-14. The working reference for building the remaining screens in this look is `docs/DESIGN_SYSTEM.md`. This **supersedes the table layout** described under "Layout" in Session 13 and "Layout of the message row" in Session 14: the class list is now a grid of ticket cards, and a failed apply is a `role="alert"` message inside that class's card, not a table row.

### Direction
Deep bottle green, warm cream paper, one vermilion action colour (white on it is 4.85:1), gold for "on hold". Chosen to read as a school and a national context without the usual purple-on-white product look. The one memorable device is the **admission ticket**: each class is a card with a perforated tear line (a dashed rule with a bite out of each end, drawn in the page colour) above its apply stub, and a strip of 30 "seat" segments in place of a table row. The hero carries a grain texture and a large rising-sun disc. One fixed light theme (`color-scheme: light`); **no dark mode**, deliberately: it would double every colour decision and every check for no launch benefit.

### Tokens, not literals
Every colour, font, radius, shadow and easing is a CSS variable in `src/styles/tokens.css`; components never hard-code one. Shared pieces (buttons, badges, cards, form fields, message cards, spinner, skeleton, the number animation) are in `styles/base.css` and `styles/components.css`, loaded once from `main.tsx`; styling that belongs to one component stays beside it. This is what lets the screens still to be built look the same without each inventing a look. A convention in `AppLayout.css`: every direct child of `<main>` is a centred column, except an element with class `hero`, which runs full width. A screen that is only a heading therefore still aligns, and no placeholder page had to be edited.

### Type: self-hosted, and kept small
Fraunces (variable, weight and optical size) for headlines and the big seat numbers; Hind Siliguri for everything else, chosen because it has real Latin **and Bangla** glyphs, so "আবেদন করুন" is not set in a fallback. Both come from `@fontsource` (pinned exactly), so launch does not depend on a font CDN. **A mistake caught by measuring:** the first version imported each script's file separately (`latin-400.css`, `bengali-400.css`). Those files declare **no `unicode-range`**, so the browser treats each as needed for every character, and a visit downloaded every Bengali weight (about 73 KB each) plus a Bangla serif (82 KB) to show one button and one word: roughly 500 KB of fonts. The combined files (`400.css`) do declare the ranges, so a script's file is fetched only when that script is on screen. Also dropped: weight 700 (bold is mapped to 600 in `base.css`) and Tiro Bangla (82 KB to set one word; Bangla inside a heading now falls back glyph by glyph to Hind Siliguri). Measured in the browser: a fresh load of the class list fetches exactly five font files (Fraunces Latin, Hind Siliguri Latin 400/500/600, Hind Siliguri Bengali 600), about **186 KB** from the build's file sizes.

### The seat strip must not lie (`src/pages/classSeats.ts`)
The strip is a rounded picture of the real numbers, so rounding must never say something the numbers do not. `seatSegments()` guarantees: the three parts add up to the strip length; a class with even one seat left always shows at least one free segment; a sold-out class shows none; any confirmed or held seat shows at least one segment of its own. This was property-tested (every combination for classes of up to 60 seats, 39,710 of them, plus 200,000 random ones for classes of up to 5,000 seats, and the .5-rounding and last-seat cases; 239,710 in all) with a throwaway script outside the repo, because **the frontend has no test runner** (the same gap Sessions 12-14 recorded). Status: `full` at 0 left, `filling` at 20% or less left, otherwise `open`. When a class is full but seats are on hold, the card says they may reopen, which is true under the hold rules.

### Accessibility, checked rather than assumed
Text and control contrast was computed for 25 pairs actually used (all meet WCAG: 4.5:1 for text, 3:1 for large text and control edges; the tightest is white on vermilion at 4.85:1). One finding: the existing divider colour is only 1.36:1, far too faint for the edge of an input, so form fields use a separate `--field-border` (3.55:1). Also: a skip link; one focus ring everywhere; `lang="bn"` on Bangla strings (Bangla gets extra line height); the seat strip is `aria-hidden` and the same numbers are written beside it; the loading skeleton keeps a `role="status"` "Loading classes…"; the apply button keeps its `aria-label` and `aria-busy`. **Motion** (entrance, the number dropping in when a count changes, the pulsing live dot) is switched off by `prefers-reduced-motion` in one global rule. Entrance animations use `animation-fill-mode: backwards`, because `both` would pin the end state and override the hover lift.

### Navigation and chrome
There was no way to reach `/me` from the UI. The header now has "Classes" and "My applications"; the admin create-class page is deliberately **not** linked (the spec calls it admin-only in spirit), though its URL still works. The registration-number input keeps its logic exactly (same draft state, same 17-digit validation, same messages and `aria` wiring, same `localStorage` write) and is restyled as a capsule on its own bar under the header. ## Session 17 — Application status screen (`/holds/:holdId`)

Scope: this screen only (poll, countdown, confirm, cancel, their errors). No my-applications screen, no central error mapping, no change to the backend.

### Which status is shown (`resolveHold`, `src/pages/holdCountdown.ts`)
The server is the source of truth. The one exception is a stand-in: when the latest server answer says HELD and the countdown has reached zero, the page shows EXPIRED at once instead of waiting for the next poll.
- A server status other than HELD is shown as it is, whatever the clock says. A student who confirmed on another device a moment before the deadline must not be told the hold expired.
- The stand-in applies only while the latest answer **arrived before the deadline** (`fetchedAt < expiresAt`, both on this device's clock). Such an answer says nothing about the deadline. As soon as an answer arrives from after it, that answer decides: EXPIRED, or, if the server still says HELD, HELD with the caption "Checking with the server…" (`serverDisagrees`). The alternative, keeping EXPIRED until the server agrees, would leave a student with a fast clock unable to pay for a seat the server would still sell them.
- Confirm is off when the countdown is at zero even if the server says HELD (the rule as given: "disabled when status is not HELD or the countdown has hit zero"); cancel is off only when the status shown is not HELD.

### The clock (`useNow`)
A 1 s interval alone would show the flip up to a second late, so a timeout is also set for the deadline itself, 10 ms past it (browsers can run a timeout a millisecond early as `Date.now()` reads it, which would leave one extra second on 00:00). The countdown text is rounded **up** to whole seconds, so it shows 00:01 until the last instant and 00:00 exactly when the page flips. Both timers run only while the server says HELD (every other status is final), and the time is renewed on `visibilitychange`, because background tabs throttle timers. The `setTimeout` limit (2^31 - 1 ms) is guarded.

### Polling policy
`refetchInterval` is a function: 4000 ms, `false` once the data holds CONFIRMED, EXPIRED or CANCELLED (the backend never leaves those states, and the lazy-expiry rule means EXPIRED is final too), and `false` after a 404 (the hold does not exist and will not). No retry, as in `useClassList`; the same remembered-last-error device keeps the failure from flipping to a spinner on every poll. The poll is not gated on the student id and its key has none, because `GET /holds/{holdId}` takes no `X-Student-Id` (API contract); a hold's status is not private to its owner there.

### Actions
- **Confirm** writes the 200 body's status (CONFIRMED) into the cached hold, then invalidates it. Without the write the page would keep an enabled button until the refetch landed; the write is the server's own answer, not a guess. It is also invalidated after a failure, since a 409 means the hold is not what the page thought. The class list is invalidated too (a held seat became a confirmed one).
- **Cancel** marks the cached hold CANCELLED and navigates to `/`; Back then shows CANCELLED rather than a hold that is gone. On failure it stays and refetches. The class list is invalidated either way (a seat is freed). The hold is deliberately not invalidated after a success: the observer is about to unmount, and a request for a page nobody sees would only be cancelled.
- Each button is off while either action is in flight, so there is no double submit and no confirm racing a cancel. Starting one action clears the other's old error, so at most one message shows.
- The messages are the backend's own, as in Session 14 (no code table). After a 409 the refetch changes the status panel to match, and the message stays under the buttons to say why.

### The clock-ahead limit, and its fix
Everything above compares `expiresAt` (the server's clock) with `Date.now()` (the device's). A device clock N seconds ahead shows HELD at 00:00 with confirm off for about N seconds before the server's EXPIRED arrives (measured: 15 s ahead gave 12 s). The page needs the server's time to correct for it. The `Date` response header would do, but a browser may read it cross-origin only if the CORS policy exposes it, and `CorsSetup.cs` exposes just `X-Correlation-Id`; the other route is a server-time field in `GET /holds/{holdId}`, which the frozen contract does not allow. So the limit stays, shown honestly on screen instead of hidden, until the backend exposes `Date`.

## Session 18 — Create class screen (`/admin/new-class`)

Scope: this screen only. No change to the class list, the apply flow, the status screen or the backend; one shared style block (`state-card--success`) was added to `styles/components.css`.

### Success: a message, then the redirect, on a timer owned by the page
The brief says "show a success message and redirect to `/`". ### One request per submit: a latch, not a re-render
From a submit until the redirect the form is locked (`<fieldset disabled>` and a disabled button, so Enter cannot submit either). That alone was **not enough**: `locked` only becomes true after a re-render, and TanStack Query's `notifyManager` reports `isPending` a tick after `mutate`, so a second submit in that gap passed the guard. A synchronous triple submit in the browser sent three `POST /classes` and created three classes. A human double click is slower than the gap, but this POST is not idempotent (a repeat is a second class, not a 409), so the guard must not depend on timing. A `useRef` latch is set the moment a request is sent. On success it stays shut (the page is locked until the redirect); on failure `mutate`'s per-call `onError` opens it so the student can fix the values and try again. After the fix, three submits sent one POST. The latch lives in the page because it guards that page's submit handler.

### Browser-side rules mirror the backend, and are stricter where the backend would answer with framework wording
`validateClassForm` (`src/pages/createClassForm.ts`, pure, no React) follows `CreateClassRequestValidator` and the DTO: name trimmed, not empty, at most 200 characters (`CLASS_NAME_MAX_LENGTH`; JavaScript and .NET both count UTF-16 units, and the trimmed name is what is sent); seats greater than 0. The brief says only "number > 0", but the backend's `TotalSeats` is a C# `int`, so `1.5`, `1e30` or `2147483648` would be refused at model binding with the framework's wording (Session 6, "Known and left as is"). The rule is therefore **digits only, greater than 0, at most 2,147,483,647**, which also makes `1e3`, `1.0`, `+5` and `-5` errors: a seat count is a whole number, and one rule is easier to explain than "numbers the backend can parse". Messages: `0` says "must be greater than 0"; anything that is not digits says "must be a whole number greater than 0, for example 120".
- **`type="number"` is kept** (the numeric keyboard and stepper on a phone). Its weakness is that text the browser cannot read (`1e`, `-`) comes back as an **empty** `value`, which would be reported as "enter the number of seats". The `change` handler therefore records `validity.badInput`, and `validateClassForm` takes it as `seatsUnreadable`.
- Errors appear **after the first submit attempt** and then follow every keystroke, so a field is not shouted at while it is first being typed; focus moves to the first invalid field on a failed submit, `aria-invalid` is set and `aria-describedby` lists the hint and the error. `noValidate` stays on the form so the browser's own bubbles never compete with these messages.

The list screen is not mounted while this one is, so its query has no observer, and the default invalidation (active queries only) would only mark it stale; the class list would then show the old list for one request on arrival. `refetchType: "all"` refetches it in the background during the 1.8 s, and the new class was on the list at arrival (a `GET /classes` seen during the success window). The returned promise is **not** awaited in `onSuccess`: the message must not wait for a refetch. If the list had never been loaded there is nothing to refetch, and the list fetches normally on mount.

## Session 20 — Frontend image (nginx, runtime `config.js`, test stage) and its compose service

Scope: `frontend/Dockerfile`, `nginx.conf`, the start-up script, `.dockerignore`, `.gitattributes`, the compose `frontend` service, and the CORS default. No application code changed.

### One Dockerfile, four stages, and why the tests are one of them
`deps` (`node:22-alpine`, `npm ci`) is shared by `test` (`npm test`), `build` (`npm run build`) and the last stage (`nginx:alpine`, copying only `dist/`). `docker build --target test ./frontend` therefore runs the whole suite with nothing but Docker, on Node 22, and fails the build when a test fails. `docker compose up` builds the **last** stage only: BuildKit (the default builder since Docker Engine 23) skips stages the target does not depend on, so starting the stack never runs the tests. This relies on BuildKit; the legacy builder would run every stage in order.
- **No `# syntax=` line.** It makes BuildKit pull a frontend image from Docker Hub before anything else; here that stalled the whole build on a slow network, and nothing in the file needs it.
- **npm is told to be patient** (`NPM_CONFIG_FETCH_RETRIES=5`, a 5-minute fetch timeout, a retry back-off) and `npm ci` runs with a BuildKit cache mount on `/root/.npm`. The first build here failed with `ETIMEDOUT` from the registry; with the cache a retried build keeps what it already downloaded instead of starting again.
- `.dockerignore` keeps `node_modules`, `dist`, `coverage` and `.git` out of the context; it also means the image is built from the sources, never from the host's `node_modules` (a Windows install would carry the wrong native binaries into a Linux image).

### Runtime config: a script in `/docker-entrypoint.d`, not a rebuild
The nginx image runs every executable script in `/docker-entrypoint.d` before it starts nginx. `40-runtime-config.sh` writes `/usr/share/nginx/html/config.js` from `API_BASE_URL` (default `http://localhost:8080`), so one image serves any backend (Session 11's decision). The value is written as a **JSON string**: line breaks are dropped, then backslashes and double quotes are escaped with `sed`, so a stray character cannot end the string literal. Dropping `envsubst` for this avoids a second, unescaped way to inject the value.
- **`API_BASE_URL` is what the browser calls, not what the container calls.** Under compose it is `http://localhost:${API_PORT:-8080}`; it follows `API_PORT`, so changing the published API port keeps the two in step. `http://backend:8080` would be wrong for the reason already recorded under "Correction to the repository-layout note": a browser on the host cannot resolve a compose service name.
- The script has LF line endings enforced by `frontend/.gitattributes` (`*.sh text eol=lf`); this repo is edited on Windows with `core.autocrlf=true`, and a CRLF shebang line makes the container fail with `/bin/sh^M: not found`. The Dockerfile also strips `\r` and sets the executable bit, so a checkout that ignores `.gitattributes` still works.

### nginx
`try_files $uri /index.html` for everything except two paths, so a refresh on `/holds/h_1` or `/me` returns the app, not a 404. `/config.js` is `no-store` and is `try_files /config.js =404`: it is never answered with `index.html`, because an HTML page served for a script URL fails with a syntax error the app cannot explain (src/config.ts already throws a descriptive error when the config is missing). `/assets/` carries content hashes, so it is `immutable` for a year; `index.html` is `no-cache`.

### Compose
`frontend` is built from `./frontend`, published on `${FRONTEND_PORT:-3000}`, and `depends_on: backend: condition: service_healthy`, which works with the backend image's own `HEALTHCHECK` on `/health` (no change to the backend). The frontend image has its own `HEALTHCHECK` (`wget` on `/`).
**CORS default** is now `http://localhost:5173,http://localhost:4173,http://localhost:${FRONTEND_PORT:-3000}`, still with `${VAR-default}` (not `:-`) so an empty `CORS_ALLOWED_ORIGINS=` still means "off". Making the third origin follow `FRONTEND_PORT` means changing the published port does not silently turn into "the browser blocks every call". If someone sets `CORS_ALLOWED_ORIGINS` themselves, the new origin has to be in their list (README, `.env.example`).

## Session 22 — Test plan run: what it showed that needs a decision

No application code changed; results are in PROGRESS.md (Session 22). Decisions about how the run was done, then the findings that need a decision from a later session.

### How the run was done
- **An isolated compose project** (`-p school-admission-e2e`, own volume, API on 8180, web app on 3100, `HOLD_DURATION_SECONDS=90`) instead of the dev stack, so test data never reached the database on :8080 and the expiry cases took minutes instead of ten minutes each. The compose file was used unchanged; only environment variables differed.
- **The second backend for TC-C02 is `docker run` of the same image on the compose network**, not `docker compose up --scale backend=2`: the service publishes a fixed host port, and two replicas cannot both bind it.
- **"Lazy expiry" is proved by ordering, not by timing luck (TC-B17).** A sweep only ever moves a row `Held` -> `Expired`. So if the API already reports the seat free at time t1 and the stored row is still `Held` when read at a later t2, no sweep had run at t1. Samples where the sweep got there first are reported as inconclusive, not as passes.
- **A latency measurement must bracket the event (TC-B18).** The first version recorded when its own polling noticed the change and reported 13.4 s; the real flip was 1.2-4.7 s after `expiresAt`. The fix is to start polling before the event and report "last seen Held" and "first seen Expired".

### Finding 1: the connection budget is not bounded, so two instances can starve each other (open)
Npgsql's default `Maximum Pool Size` is 100 per process and `docker-compose.yml` sets none, while Postgres' default `max_connections` is 100 (3 of them reserved). One instance that has seen a burst of 100 concurrent requests keeps up to 100 idle connections for 5 minutes (`Connection Idle Lifetime`), which leaves a second instance with none: its requests fail with `53300` and are answered `400 UNEXPECTED_ERROR` (the catch-all of Session 6). Seat safety is unaffected (the oversell checks live in the database), but this is exactly the two-instance deployment the concurrency bonus is about, and the symptom is a refusal that says nothing about retrying. The rule to apply: instances x `Maximum Pool Size` must stay below `max_connections` minus the reserved slots. Options not yet chosen: a `Maximum Pool Size` in the connection string built in `docker-compose.yml` (for example 30), a larger `max_connections` on the Postgres service, and a specific retryable code for `53300` in `ExceptionMapper` (today only 40001, 40P01, 55P03 and class 23 map to `CONFLICT`).

### Finding 2: where the frontend error boundary has to sit (open, for the error-handling session)
A render error today leaves `#root` empty: no header, no message. Because `AppLayout` renders the header around `<Routes>`, a boundary placed **inside** the layout around the routes would keep the header and the registration input while a failed screen shows its fallback and a retry, and a second boundary above everything is the last resort. The same session should add the `*` route (an unknown URL currently renders the shell with an empty content area) and build `/me`.

## Session 23 — My applications (`/me`), the error boundary, page not found

Scope: the three gaps the Session 22 test run found (TC-F10, TC-F12, TC-F13). No backend change, no contract change. Test-first throughout; the tests were checked by breaking the code on purpose (see PROGRESS.md).

### Two error boundaries, and what "Try again" does
- **`ErrorBoundary`** is a class component because React only catches render errors in class components. It is used twice. **`ScreenBoundary`** (in `AppRoutes.tsx`) sits *inside* `AppLayout`, around `<Routes>`: a crashed screen shows the message in the page column while the header, the navigation and the registration number input stay, so the student can still switch number or go elsewhere. **`Root`** wraps the whole provider stack in a last-resort boundary for a crash in the header or anything above the screens; its fallback uses no router, query client or context, and "Back to classes" is a plain `<a href="/">`, a full load that also clears whatever state caused the crash.
- **A crashed screen is left by navigating.** `resetKey` is the current path. It only clears a fallback that was already showing before the update: if the path changes in the same update that crashes (the student went to a screen that fails), the fallback stays instead of trying the same screen a second time.
- **"Try again" empties the query cache first** (`queryClient.removeQueries()` in `ScreenBoundary`'s `onReset`). The Session 22 failure was *data*, a response in the wrong shape; the cache keeps it for 5 minutes (`gcTime`) and would hand the same object to the screen on the next render, which would crash again at once. With the cache empty the screen starts from a fresh request. This is blunt (it drops every query), but it only runs on the retry path, and the crashed subtree has no observers left. Checked: with the reset removed, the "recovers on Try again" test fails.
- **The boundary logs** with `console.error("[ErrorBoundary] ...", error, componentStack)` because a production build of React says nothing about an error a boundary has caught; without the line a crash would leave no trace.
- **What it does not do.** It catches errors thrown while rendering. Errors in event handlers, in async code and failed requests are not caught (each screen already shows its own request failures). It *contains* a response in an unexpected shape but does not *prevent* it: no response validation was added, so a screen that receives such a response shows the crash message, not a degraded list.

### My applications (`/me`)
- **`useMyHolds()`** is gated on a registration number (`enabled`), has that number in its query key, polls every 4 s like the class list and the status screen, and keeps no retry. The key is what stops one student's list reaching another: switching numbers is a different query with no data, so the screen shows its loading state, never the previous list (tested with the second student's answer held back). Without a number there is nothing to ask and no request goes out; the screen says "Enter your registration number to see your applications."
- **The list keeps the server's order** (newest first, Session 4). Each row is one `li` with the class name as an `h2`, the same status words and badge colours as the status screen, a one-line summary and a link named "View status of <class>". A running hold also says "Hold ends <time of day>"; the other statuses have no end to tell about.
- **No per-row countdown, on purpose.** A held row can say "On hold" for up to one poll (4 s) after its deadline; the exact, second-by-second countdown belongs to the status screen the row links to. Per-row timers would add N intervals for a summary.
- **Duplication left in place:** the status words and badge classes are a small map in `MyApplicationsPage.tsx` that repeats the status screen's (whose copy is local to that file); and `useMyHolds` is the third copy of the "remember the last error until a request succeeds" device (after `useClassList` and `useHold`). A shared helper for both is still open.

### Page not found
`<Route path="*">` renders `NotFoundPage` inside the shell, so an unknown address, `/holds` with no id and `/admin` all show "Page not found" and a link to the classes instead of an empty content area.

### Test-harness changes
`expectCrash()` (`src/test/`) silences React's and jsdom's reports of an error a test throws on purpose, and returns the `console.error` spy so a test can still check what was logged. `renderWithProviders` accepts a `queryClient`: its default drops a query's data the moment nothing shows it (`gcTime: 0`), which hides exactly the cached-data bug the retry test is about.
